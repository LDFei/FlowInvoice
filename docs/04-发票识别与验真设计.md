## 1. 目标与边界

**目标**：把「票据 → 结构化字段 `{invoice_no, invoice_type, date, amount, title, ...}`」从 Mock 正则解析，升级为按票据形态自动分派的识别管线，并给真伪校验一个权威落点。

**边界（识别 ≠ 验真）**：

| | 职责 | 性质 | 是否 LLM |
|---|------|------|---------|
| **识别** | 读票面 → 结构化字段 | 理解类 | ✅ 可 LLM（抽取层） |
| **验真** | 发票真伪 / 查重 / 防篡改 | 确定性 + 可审计 | ❌ 走税局，不接 LLM |

> 一句话：**识别可以靠模型「猜」，真伪必须靠税局「验」。** 真伪属于钱与审计，LLM 幻觉不可接受。

## 2. 中国发票形态全景（2024–2026 数字化现状）

### 2.1 票种谱系

中国发票不是"一种格式"，而是一个谱系。全面数字化电子发票（数电票）自 **2024-12-01 起全国推广**，2025 年基本实现全面数字化，把传统票种统一为「电子发票」，用**业务标签**区分场景：

- **传统票种**：增值税专用发票 / 增值税普通发票 / 机动车销售统一发票 / 航空运输电子客票行程单 / 铁路电子客票 / 卷式打车票 / 定额发票 / 通行费发票 / 医疗收费票据…
- **数电票业务标签**：建筑服务、成品油、旅客运输、货物运输、不动产销售、农产品收购、差额征税、通行费、医疗服务等特定业务场景。

**关键差异**：数电票发票号码为 **20 位全国唯一码**（无发票代码），赋码制由税局系统实时生成，无法仿制、篡改。

### 2.2 数电票三种文件格式（决定识别方案的关键）

| 格式 | 角色 | 能否验签 |
|------|------|:---:|
| **XML** | **源文件**：记录全部要素 + **数字签名**（国密 SM2/SM3，税局私钥签发）；财政部入账归档标准格式 | ✅ |
| **OFD** | 版式文件：可用「增值税电子发票板式文件阅读器」查验监制章与电子签名有效性 | ✅ |
| **PDF** | 仅预览/打印，**不是源文件**，不支持验签 | ❌ |

> 铁路电子客票、航空运输电子客票行程单交付的合规文件为 **OFD**（内嵌结构化数据），其余数电票为 **XML**。

### 2.3 为什么这决定了识别方案

> **数电票 XML 直接解析即可，不存在 OCR 幻觉；OCR 只留给纸票和照片。** —— 2025 年数字化之后的标准答案。

识别引擎的价值已经从「主要手段」退为「兜底手段」：结构化源文件（XML）零成本、零幻觉；OCR 只在拿不到源文件、只有纸票或照片时才有必要。

## 3. 识别管线（按票据形态分层）——本期闭环

### 3.1 五层管线与识别契约

```
票据文件
  │  形态探测（扩展名 + 内容特征：magic number / 文件头 / 编码）
  ├─ 数电票 XML ───────────────▶ L1 XmlInvoiceParser（ElementTree，字段全 + 明细行，零幻觉）
  ├─ OFD（zip 容器）──────────▶ L2 OfdInvoiceParser（内嵌发票 XML 优先 → 版式文本按坐标还原）
  ├─ PDF ─────────────────────▶ L3 PdfInvoiceParser（内嵌 XML 附件 → 文本层 → 扫描件渲染成图）
  │                              └─ 无文字层且 OCR 未装 ──▶ OcrFailedError「组件未安装」
  ├─ UTF-8 文本 ──────────────▶ L4 TextInvoiceParser（正则；LLM 抽取为生产增强路径）
  ├─ 图片/扫描件 ─────────────▶ L5 OcrImageParser（PaddleOCR → 版面文本 → 复用 L4 抽取）
  └─ 无法识别 ────────────────▶ 退回节点（识别失败，带结构化原因 ocr_failed）
```

| 层 | 票据形态 | 技术方案 | 是否 LLM | 状态 |
|----|---------|---------|:---:|---------|
| **L1** | 数电票 XML 源文件 | ElementTree 直解析：全要素 + 数字签名 + 明细行 | ❌ | ✅ 已实现 |
| **L2** | OFD 版式文件 | zip 容器 → 内嵌发票 XML（复用 L1）→ 否则 TextObject 按 (page,y,x) 还原版式文本 | ❌ | ✅ 已实现 |
| **L3** | PDF（电子票/扫描件） | embfile 内嵌 XML 附件优先 → 文本层提取 → 无文字层渲染成图走 OCR | ❌ | ✅ 已实现（PyMuPDF） |
| **L4** | 文本票据 | 正则核心必抽；LLM 强约束 JSON 抽取为生产增强（temperature=0） | 抽取✅ | ✅ 已实现（正则基座） |
| **L5** | 图片/照片/扫描件 | PaddleOCR（PP-OCRv6，检测→识别）→ 按文本框左上角 (y,x) 恢复阅读顺序 → 复用 L4 | 引擎❌ | ✅ 已实现（真实冒烟通过） |

**识别契约分层**（`OcrTool.extract(file_path) -> dict`）：

- **核心字段**：`invoice_no / invoice_type / date / amount / title` —— 缺任一 → 抛 `OcrFailedError`，上游退回（结构化原因 `ocr_failed`）。
- **扩展字段**：`buyer_name / buyer_tax_no / seller_name / seller_tax_no / tax_amount / tax_rate / check_code / has_signature / remark / issuer / line_items` —— 尽力而为，缺失 → `null`，**不阻塞主流程**。
- **`source` 标注**：`xml / ofd / pdf / text / ocr`，记录字段从哪个形态来（审计与降级溯源）。

**分层逻辑**：按形态做「成本 × 准确率 × 速度」权衡——L1/L2 免费零幻觉；L3 吃数电票 PDF（常内嵌结构化 XML 附件）；L5 只兜纸票与照片；L4 是 OFD/PDF/OCR 三条路的共同抽取基座。

**统一入口与形态分派**：`OcrTool.extract(file_path) -> dict` 接口稳定，下游图节点零改动；解析器注册表顺序 `[Xml, Pdf, Ofd, Text, OcrImage]`，`matches(raw_bytes)` 做形态探测，新增票种只加分派项。

### 3.2 全量票面落库（表结构）

发票识别只是「读」，落库才是「用」。**方案 B：表结构全量装 + 识别全量抽**，为验真/抵扣/三单匹配留位：

- `invoices` 主表新增 11 列：`buyer_name / buyer_tax_no / seller_name / seller_tax_no / tax_amount / tax_rate / check_code / has_signature / remark / issuer / source`。
- `invoice_items` **明细子表**（一对多 1:N）：一行发票 → 多行明细（品名/规格/数量/单价/金额/税率/税额）。发票行明细天然多行，放主表是反范式；独立子表才能支持未来进项抵扣台账、三单匹配（发票-合同-收货）。
- SQLite 用 `PRAGMA table_info` + `ALTER ADD COLUMN` 幂等迁移；PG 用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`（写在 `_DDL`）。`add_invoice` 同事务写主表 + 子表，老调用（无扩展字段）向后兼容。

### 3.3 工程坑（真实冒烟暴露，已修）

| 坑 | 表现 | 修复 |
|---|---|---|
| Paddle 3.3 oneDNN/PIR 不兼容 | 图片推理崩溃 `ConvertPirAttribute2RuntimeAttribute not support`（onednn_instruction.cc:118） | `FLAGS_use_mkldnn=0` + `enable_mkldnn=False` |
| PaddleX 3.x predict 结果结构变化 | `.json` 是 `{"res": {...}}` 包装，`rec_texts` 在里层（直接取到 None） | `recognize` 解包后再取票面字段 |
| PaddleX 3.x `rec_boxes` 变扁平 | `[x0,y0,x1,y1]` 四元组（老版本是 `[[x,y],...]` 点对） | `_box_min_xy()` 兼容两种格式，取左上角排序 |

**降级哲学**：OCR 组件惰性导入——未安装 paddleocr → 图片/扫描件明确报「组件未安装」，核心 XML/OFD/PDF/文本四路不受影响（`OcrTool(image_ocr=None)`）。

### 3.4 真实生态兼容（六规则重审补：#81-83）

**XML 字段命名三套并存**（A1 重审发现：自测样例 ≠ 真实报文）：

| 风格 | 样例 | 来源 |
|---|---|---|
| camelCase | `invoiceNo / invoiceDate / totalAmount / totalTaxAmount / salerName / salerTaxNo / buyerName / buyerTaxNo` | Apifox 数电票接口规范（实证） |
| 民间英文 | `InvoiceNo / InvoiceKind / Total / TaxAmount / SellerName / SellerTaxId` | 生态流通/自测 |
| 拼音缩写 | `Fphm(发票号码) / Kprq(开票日期) / Ghdwsbh / Xhdwsbh（购/销货单位识别号）` | 金税报文 |
| 中文标签 | `购方名称 / 销方名称 / 合计税额 / 价税合计` | 版式/报销单导出 |

对策：`XmlInvoiceParser` 别名**宁广勿窄**——核心/扩展/明细字段全补三套；`find_text` 精确匹配本地名 + 逐字段独立，多别名不串字段。**价税合计**与**不含税合计**是两类（`totalAmount` vs `invoiceAmount`），报销口径只认含税合计，防少报税差。

**顶层形态分派降级边界**（A2）：除 Xml 外每层内部都有自降级（OFD 内嵌→版式、PDF→文本→OCR、L4 正则→LLM），唯顶层分派曾"命中即终局"。现在 `OcrTool.extract` 对 Xml 解析失败分两类处理：

- **含发票结构化标记**（`_looks_like_invoice_xml`）→ 确属发票但本层不识别/残缺 → **保留具体缺字段报错**，不降级（防未知 schema 真发票的报错被 OCR 噪音淹没）；
- **无发票标记** → Xml 宽嗅探（`<` 开头）误命中（HTML/随机 XML/带 XML 头的文本票）→ **放行后续形态**（文本正则/LLM 兜底救回）。

PDF/OFD/文本/OCR 的 `matches` 是强嗅探，失败仍即时报错。另：`_looks_like_invoice_xml` 嗅探标记同步补 camelCase/拼音/中文，嵌入 OFD/PDF 的 XML 附件不因命名风格漏判。

## 4. 验真 / 验签（权威真实性，非 LLM）

### 4.1 税局查验（真伪）

- **全国增值税发票查验平台**（`https://inv-veri.chinatax.gov.cn`）：输入 20 位发票号码 + 开票日期 + 开具金额（不含税）→ 返回真伪；数电票可上传 XML/OFD 文件校验，验证通过即代表发票真实有效且电子签章有效。
- 企业通常经**聚合服务**（百望/诺诺/航信等）封装该接口，统一鉴权与限流。

### 4.2 电子签名校验（防篡改）

- 数电票 XML 内嵌**数字签名**（国密 SM2/SM3，税局私钥签发），可校验：签名证书有效性、签名值是否匹配、文档是否被篡改。
- OFD 用官方阅读器验签；**PDF 不支持验签**（所以入账必须保存 XML 源文件）。

### 4.3 与识别的边界 / Demo 落点

- `verify` 节点的 **Mock 即代表「税局查验 API + 电子签名校验」**（对应 docs/01 §6 `InvoiceVerifyAdapter`，真实实现 = 国家税务查验 API / 第三方）。
- 后续可选：加「签名字段存在性 + 防篡改」模拟校验节点，把"权威真实性"在 Demo 里演出来（本期不做，见 §6 演进）。

## 6. 演进与接口约定

1. **接口稳定**：`OcrTool.extract(file_path) -> dict` 不变；识别契约分核心/扩展两层，新增字段只加扩展层，下游图节点与测试零改动。

## 7. 面试叙事

1. **「数电票 XML 直接解析，不存在 OCR 幻觉；OCR 只留给纸票和照片」**——知道 2025 年发票全面数字化，证明对行业现状有认知。
2. **识别分层 = 成本/准确率/速度的权衡**：免费零幻觉（XML）→ 毫秒级高吞吐（PaddleOCR）→ VLM 兜底复杂版式（不为 2% 场景付全部 GPU 成本）。
3. **权威真实性靠税局 + 国密签名，不是 LLM**：审计可复现，AI 不碰钱的真伪——与 docs/03「混合决策」（LLM 决策 + 工具执行 + 规则兜底）同一套设计语言。
4. **识别 ≠ 验真**：模型负责「读」，税局负责「证」，职责分离让「AI 提效」与「审计可信」同时成立。
