## 1. 目标与边界

**目标**：把「票据 → 结构化字段 `{invoice_no, invoice_type, date, amount, title, ...}`」从 Mock 正则解析，升级为按票据形态自动分派的识别管线，并给真伪校验一个权威落点。

**边界（识别 ≠ 验真）**：

| | 职责 | 性质 | 是否 LLM |
|---|------|------|---------|
| **识别** | 读票面 → 结构化字段 | 理解类 | ✅ 可 LLM（抽取层） |
| **验真** | 发票真伪 / 查重 / 防篡改 | 确定性 + 可审计 | ❌ 走税局，不接 LLM |

> 一句话：**识别可以靠模型「猜」，真伪必须靠税局「验」。** 真伪属于钱与审计，LLM 幻觉不可接受。

## 2. 中国发票形态全景（2024–2026 数字化现状）

### 2.1 票种谱系

中国发票不是"一种格式"，而是一个谱系。全面数字化电子发票（数电票）自 **2024-12-01 起全国推广**，2025 年基本实现全面数字化，把传统票种统一为「电子发票」，用**业务标签**区分场景：

- **传统票种**：增值税专用发票 / 增值税普通发票 / 机动车销售统一发票 / 航空运输电子客票行程单 / 铁路电子客票 / 卷式打车票 / 定额发票 / 通行费发票 / 医疗收费票据…
- **数电票业务标签**：建筑服务、成品油、旅客运输、货物运输、不动产销售、农产品收购、差额征税、通行费、医疗服务等特定业务场景。

**关键差异**：数电票发票号码为 **20 位全国唯一码**（无发票代码），赋码制由税局系统实时生成，无法仿制、篡改。

### 2.2 数电票三种文件格式（决定识别方案的关键）

| 格式 | 角色 | 能否验签 |
|------|------|:---:|
| **XML** | **源文件**：记录全部要素 + **数字签名**（国密 SM2/SM3，税局私钥签发）；财政部入账归档标准格式 | ✅ |
| **OFD** | 版式文件：可用「增值税电子发票板式文件阅读器」查验监制章与电子签名有效性 | ✅ |
| **PDF** | 仅预览/打印，**不是源文件**，不支持验签 | ❌ |

> 铁路电子客票、航空运输电子客票行程单交付的合规文件为 **OFD**（内嵌结构化数据），其余数电票为 **XML**。

### 2.3 为什么这决定了识别方案

> **数电票 XML 直接解析即可，不存在 OCR 幻觉；OCR 只留给纸票和照片。** —— 2025 年数字化之后的标准答案。

识别引擎的价值已经从「主要手段」退为「兜底手段」：结构化源文件（XML）零成本、零幻觉；OCR 只在拿不到源文件、只有纸票或照片时才有必要。

## 3. 识别管线（按票据形态分层）

```
票据文件
  │  形态探测（扩展名 + 内容特征）
  ├─ .xml/.ofd ────────────▶ L1 结构化解析（ElementTree / lxml）
  ├─ 扫描件/照片 ──────────▶ L2 PaddleOCR 引擎 → LLM 抽取
  │                          └─ 低置信度/复杂版式 ─▶ L3 多模态 VLM
  ├─ .txt（Demo 现状） ────▶ L4 LLM 抽取（无 key 降级正则）
  └─ 无法识别 ──────────────▶ 退回节点（识别失败，带原因）
```

| 层 | 票据形态 | 技术方案 | 是否 LLM | 落地阶段 |
|----|---------|---------|:---:|---------|
| **L1** | 数电票 XML/OFD 源文件 | 直接结构化解析，字段全、零幻觉、最快 | ❌ | 生产优先路径；Demo 预留接口 |
| **L2** | 纸票/拍照扫描件 | PaddleOCR（PP-StructureV3：检测→识别→版面，中文、CPU 可跑、毫秒级）→ 散文本 → **LLM 强约束 JSON 抽取**（temperature=0） | 引擎❌ + 抽取✅ | 生产路径 |
| **L3** | 复杂版式（手写/异形/无框线表格） | 多模态 VLM（Qwen2.5-VL 等，图 → 结构化 JSON），PaddleOCR 低置信度时触发 | ✅ | 生产路径 |
| **L4** | 文本票据（Demo 现状） | LLM 读文本 → JSON；无 key 降级现有正则 | ✅ | **本期可实现** |

**分层逻辑**：按形态做「成本 × 准确率 × 速度」权衡——L1 免费零幻觉；L2 毫秒级高吞吐兜底大多数纸票；L3 只处理 L2 搞不定的少数复杂版式，避免为 2% 的场景付全部 GPU 成本。

**统一入口与形态分派**：`OcrTool.extract(file_path) -> dict` 接口保持不变（下游节点零改动），内部按形态分派到各层；形态探测 + 分派表注册式扩展，新增票种只加分派项。

## 4. 验真 / 验签（权威真实性，非 LLM）

### 4.1 税局查验（真伪）

- **全国增值税发票查验平台**（`https://inv-veri.chinatax.gov.cn`）：输入 20 位发票号码 + 开票日期 + 开具金额（不含税）→ 返回真伪；数电票可上传 XML/OFD 文件校验，验证通过即代表发票真实有效且电子签章有效。
- 企业通常经**聚合服务**（百望/诺诺/航信等）封装该接口，统一鉴权与限流。

### 4.2 电子签名校验（防篡改）

- 数电票 XML 内嵌**数字签名**（国密 SM2/SM3，税局私钥签发），可校验：签名证书有效性、签名值是否匹配、文档是否被篡改。
- OFD 用官方阅读器验签；**PDF 不支持验签**（所以入账必须保存 XML 源文件）。

### 4.3 与识别的边界 / Demo 落点

- `verify` 节点的 **Mock 即代表「税局查验 API + 电子签名校验」**（对应 docs/01 §6 `InvoiceVerifyAdapter`，真实实现 = 国家税务查验 API / 第三方）。
- 后续可选：加「签名字段存在性 + 防篡改」模拟校验节点，把"权威真实性"在 Demo 里演出来（本期不做，见 §6 演进）。

## 6. 演进与接口约定

1. **接口稳定**：`OcrTool.extract(file_path) -> dict` 不变；内部加形态探测分派，下游图节点与测试零改动。
2. **落地次序**：本期 L4（文本票 LLM 抽取，无 key 降级正则）→ 后续 L1（XML 解析，配一张示例数电票 XML）→ 生产 L2/L3（PaddleOCR + 多模态）与验真聚合 API。
3. **可插拔**：识别引擎、验真服务均走适配器/配置（对应 docs/01 §6、§7），替换真实服务只改装配，主流程不动。

## 7. 面试叙事

1. **「数电票 XML 直接解析，不存在 OCR 幻觉；OCR 只留给纸票和照片」**——知道 2025 年发票全面数字化，证明对行业现状有认知。
2. **识别分层 = 成本/准确率/速度的权衡**：免费零幻觉（XML）→ 毫秒级高吞吐（PaddleOCR）→ VLM 兜底复杂版式（不为 2% 场景付全部 GPU 成本）。
3. **权威真实性靠税局 + 国密签名，不是 LLM**：审计可复现，AI 不碰钱的真伪——与 docs/03「混合决策」（LLM 决策 + 工具执行 + 规则兜底）同一套设计语言。
4. **识别 ≠ 验真**：模型负责「读」，税局负责「证」，职责分离让「AI 提效」与「审计可信」同时成立。
